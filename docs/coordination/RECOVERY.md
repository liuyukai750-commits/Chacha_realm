# 并行任务故障隔离与恢复协议

## 原则

任何单个 Codex 任务都不是项目的唯一状态真源。可恢复状态必须存在于本地 Git commit、共享契约或总控状态表中；不得只保留在某个任务的对话记忆里。

## 心跳与检查点

- 每个任务完成一个可独立说明的行为后立即创建本地 commit，不累积超大未提交改动。
- 长任务至少在完成目录骨架、核心行为、测试三个阶段分别形成检查点。
- 任务需要等待依赖时，先提交当前可用状态，再向总控报告阻塞。
- 不启动需要人工长期看守的开发服务器、监听器或无限循环。

## 总控等待策略

- 总控使用有上限的批量状态快照，不对任一任务无限等待。
- 一个任务无新进展时，其他任务继续工作和集成。
- 总控按 commit 集成，不直接复制任务未提交的工作目录。
- 功能缺失可以由安全回退或明确的 unavailable 状态承接，不伪造成功。

## 故障恢复

1. 首次无响应：读取任务最近状态和分支 HEAD，不影响其他任务。
2. 连续无响应或会话崩溃：中断旧任务，保留其 worktree 和分支。
3. 分支存在有效 commit：从最后 commit 创建替代任务继续。
4. 只有未提交改动：先只读检查 diff；可验证且属于该任务范围时，由总控建立恢复提交，再创建替代任务。
5. worktree 损坏：从主分支与已集成 commit 重建新 worktree；不删除原目录，直到恢复验证完成。
6. 某功能无法按时恢复：通过 feature boundary 隔离，其他功能继续构建、测试和交付，并在状态表标明缺口。

## 集成失败回退

- 每个工作流单独 cherry-pick；一条线冲突不阻止其他无关提交。
- 集成后立即运行该工作流最小测试，失败时只撤销本次未发布集成，不改写其他任务历史。
- 根级配置和 lockfile 仅由总控修改，减少最常见的跨任务冲突。
- 契约变更先广播、后编码；未获接受的契约分叉不得进入主分支。

## 完成判定

任务只有同时满足“提交存在、验证结果已报告、契约变化已说明”才算可集成。对话显示完成但没有 commit，不视为可恢复交付。
